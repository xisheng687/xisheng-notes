最近我在用 AI 开发两个工具，遇到了一个问题：功能越加越多，做出来的东西却越来越偏离最初的想法。继续往下改，连我自己都快说不清，到底要做什么了。

所以，我暂停了一部分开发，重新梳理需求，也把以前看过的小排老师的几篇文章翻出来复习。

这次带着实际问题去看，很多方法才真正理解。

我也开始在项目里，让 Claude Code 调用 Codex，一起研究材料、起草和修改需求文档。

下面把学到的方法，以及自己整理的提示词分享出来。

## 一、几个要点

从小排老师的文章里，我整理出了这几点最重要：

1.**先说清需求。**

开发前必须说清楚需求，要给谁用、解决什么问题。

推荐使用语音输入法（比如微信输入法），可以一口气说个几分钟，把自己的想法全说出来。

然后让 AI 读现有代码或者直接复述他的理解，把需要你决定的问题提出来。

2.**把讨论结果写成文档。**

复杂需求要先整理成文档，比如技术文档，PRD 文档。

用文档沉淀下来，不但可以方便跨窗口，也方便换工具继续工作。

3.**能画出来的就别只靠文字。**

很多东西文字表达不清楚，但是一图胜言，哪怕是用草稿纸画一下发给 ai 也可以。

用表格讲规则，用流程图讲步骤，用原型图确认界面的布局。

你自己画，让 ai 画，都可以。

![](https://xisheng687.github.io/xisheng-notes/assets/posts/2026-09-09-ai-leading-ai-dev-method/body-01.png)

4.**让不同 AI 互相检查。**

方案可以交叉评审，代码写完也可以找另一个 AI 挑问题。

比如我习惯把写好的代码交给 codex 做初审、让 claude 做终审。

## 二、怎么让 AI 带着 AI 干活？

我们知道，不同的 ai 都有自己的“个性”，所以调用不同的 ai 去互相检查，互相审核，更有可能发现开发过程中的 bug 或者考虑不到的点。

我目前采用的分工是：自己主要和 Claude Code 沟通，让它安排 Codex 研究、写文档或实现，再检查结果，有问题就继续修改。

如果要作图、做视频，就调用 grok build cli。

如果已经在用 Claude Code，可以安装这两个工具：

**OpenAI 的 Codex 插件**：仓库名是 openai/codex-plugin-cc，用来连接 Codex。还需要可用的 Codex CLI 和登录状态。

**xAI 官方 Grok Build CLI**：需要多一个独立检查者时再加入，不是入门必装项。grok 的好处的能作图、做视频，而且量大优惠，很适合比如做文章配图或者简单事情打杂。

工具接通后，日常可以直接用自然语言安排工作，不必每次记命令。

## 三、常用提示词

**第一次接通工具：**

打开，claude，输入：

> 请帮我接通 OpenAI 的 Codex 插件 openai/codex-plugin-cc和xAI 官方 Grok Build CLI，检查安装、登录和调用，并用一个小任务验证。接通后，把用法写进项目规则。需要额外评审时，再检查 xAI 官方 Grok Build CLI。

**开始新项目，或者准备增加功能：**

打开，claude，输入：

> 先不要写代码。我的想法是：【填写想法】。

> 请和 Codex 一起讨论，整理目标用户、核心流程、第一版范围和完成标准。已有项目先读代码，把需要我决定的问题列出来，确认后再形成 PRD 和技术方案。

**确认页面和交互：**

> 请根据需求画出线框图和页面跳转图，说明主要按钮点下去会怎样，失败或没有操作时又会怎样。检查需求、原型和 UI 有没有前后矛盾，再交给我看。

**开发完成后：**

> 请找codex 帮忙检查实际改动，再运行相关测试。发现问题就给出具体证据并修正。最后告诉我完成了什么、哪些测试通过、还有什么没验证。

**AI 的“人工”检查：**

得益于 gpt6 变态的电脑控制能力，开发好之后，很多功能可能可以用，但是用户体验不好，那么就可以让 codex 去做“人工检查”。

> 我已经开发好了，现在请用浏览器打开网站，然后从一个陌生用户（并没有预先知道这个网站的功能）的角度，完整地体验一下这个网站的各个功能，找出用户体验不合理，用户可能感到困惑的点，梳理出来。

## 四、先做 Demo

有时候，看完文档和原型，我还是不容易想象最终效果。

我现在有一个新的思路，就是让 AI 先做一个能点、能看的 Demo 网站。

而且现在 codex 自带 site 站点功能，demo 网站也可以直接部署。

![](https://xisheng687.github.io/xisheng-notes/assets/posts/2026-09-09-ai-leading-ai-dev-method/body-02.png)

提示词可以是：

> 根据已确认的需求做一个可点击的 Demo，让我体验主要页面和操作流程。演示数据请标明，暂不接真实业务数据。

> 开发好之后利用 codex 的 site 站点功能部署，仅限我可见。好了之后直接打开给我看。

> 等我确认方向，再进入正式开发。

比如我最近在开发一个统一管理上网配置的后台。 把代理线路、网站访问规则和不同人的需求组合好，生成一条订阅链接，交给同事的电脑或手机上的 Clash 使用。

我就让 codex 先做prd 文档整理、画出线框图和跳转图、然后生成一个 demo网站出来。

我先确定自己的需要，确定好之后，再把这些资料交给 claude 开始开发。

![](https://xisheng687.github.io/xisheng-notes/assets/posts/2026-09-09-ai-leading-ai-dev-method/body-04.png)

这样，我可以直接指出“这里不对”“这一步多余”，更容易把想法讲清楚。

当然，Demo 确认的是体验和方向，不代表正式功能已经完成。

对了，如果你对页面要求很高，喜欢美观一点，还有最后一招。

让 codex 先利用自带的作图功能，把网站每个页面都先画出来，然后结合 demo网站再一起丢给 ai 去开发。
